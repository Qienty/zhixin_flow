# 下一步计划书：从可安装网页到上架的手机应用

状态日期：2026-11-23。基线：当前是**可安装 PWA**（装到主屏、离线可用、手机端验收 0 错误 0 提醒），下一步是**原生安装包**，先覆盖国内 Android 应用商店与 iOS 中国区。

这份计划书只回答三件事：先做什么、怎么算做完、什么时候需要你拍板。

## 一、完成的定义

到终点时应该能说清下面每一条，做不到就不算完成：

| 维度 | 完成的判定 |
|---|---|
| 形态 | iPhone 与 Android 各有一个安装包，双击图标进入，无地址栏、无浏览器 UI |
| 登录 | 首次打开可注册/登录，杀进程重开仍是登录态 |
| 核心流程 | 记录、练习、每周证据卡在壳内全部可用 |
| 离线 | 断网可打开外壳与已加载内容，联网后自动恢复 |
| 语音输入 | 壳内可用（WebView 的 `SpeechRecognition` 不可用，这是必改项） |
| 发布 | Android 走国内应用商店（华为 / 小米 / OPPO / vivo / 应用宝）内测，iOS 走 TestFlight 内部测试，各至少 10 台真实设备通过 |
| 质量 | 冷启动 < 2.5s（中端机）、30 分钟连续使用无崩溃、崩溃率 < 0.5% |

## 三、开工前必须先做的三个验证（PoC，2—3 天）

这三件事决定后端要不要改，**做错方向后面全白干**，所以先各花半天到一天验证，不做设计讨论。

### PoC-1：壳内调远程 API

用 Capacitor 起一个空壳，加载现有 `frontend/`，配 `server.url` 指向本机开发服务，验证能否打开页面并发出请求。产出：壳内跑通 `/api/meta`。

### PoC-2：登录方案二选一（**已定：B**）

| 方案 | 做法 | 代价 | 结论 |
|---|---|---|---|
| A. Cookie + 同源 | 壳内 `server.url` 指向你的 HTTPS 域名，页面与 API 同源，Cookie 照旧 | 需要固定域名；离线能力受 `server.url` 影响 | 不采用 |
| B. Bearer Token | 登录返回 token，壳内放存储，请求带 `Authorization` | 后端加一层校验 | **已采用** |

**决策（2026-11-23）**：选 B。已经落地（见第四节「B 方案实现记录」），网页端继续用 HttpOnly Cookie，壳内用 Bearer，两条凭据共用同一张 `sessions` 表——所以退出、改密码、过期清理对两边同时生效，不存在第二套会话状态。

### PoC-3：壳内复跑手机端验收

把 `tests/mobile_audit.mjs` 的 base URL 换成壳内地址，验证同一套指标在 WebView 里成立（安全区、软键盘、触控目标）。产出：PASS/FAIL 列表。

**PoC 之后写一页结论**，把选定方案、需要后端改的接口清单固定下来，再进入阶段 A。

## 三点五、B 方案实现记录（已完成）

| 项目 | 实现 | 验证 |
|---|---|---|
| 凭据解析 | `backend/app/api/core.py` 的 `_bearer()` 解析 `Authorization: Bearer`，优先于 Cookie | 单测 + 真实 HTTP |
| 发放规则 | 只有带 `X-Tether-Token-Auth: bearer` 的客户端才在响应体拿到 token；网页只拿 Cookie | 网页响应体无 token（已测） |
| 前端存储 | `frontend/js/api.js`：壳内（`capacitor:` / `file:` / `window.__TETHER_NATIVE__`）才把 token 写本地存储并自动带 `Authorization` | 前端测试覆盖冷启动恢复 |
| 退出 | 同时销毁请求里的 Bearer 与 Cookie 会话 | 退出后复用同一 token 返回 401 |
| 失效 | 任何 401 都会清掉壳内 token，避免带废 token 反复 401 | 前端单测 |
| 安全 | token 长度做区间校验；网页端 token 不下发给 JS，XSS 偷不到 | 畸形/伪造 token 全部 401 |

**已完成**：`TETHER_ALLOWED_ORIGINS` 白名单已经落地（逐字匹配、不支持通配、`http(s)` 的本机来源默认放行），就是阶段 A 的 A4。
