## 一、结论与范围

原报告指出了多处真实问题，但不宜直接按其优先级和修复方案实施。它混合了可复现缺陷、工程优化、产品取舍和未经充分验证的推断；部分事实、因果解释及影响范围需要修正。

本轮最重要的更正：

1. **默认 DeepSeek 模型及参数并非已证实错误。** 截至本报告日期，官方文档明确支持 deepseek-flash 及 reasoning_effort=low/high/max。[S1][S2] 原报告将这一待核实项归入遗留 P0，依据不足。
2. **413 的断连现象能复现，但不是“先设置 close_connection 就立即关闭连接”。** 只发送超限长度请求头可收到完整 413；一次性上传 8 MiB + 1 字节时，本机客户端出现连接中止。
3. **导入确有逐条查询及退化风险，但“没有可用索引”不成立。** 实际查询使用索引，索引选择和候选集大小影响性能；本机 5000 条导入实验未接近 30 秒。
4. **401 浮层问题应限定到表达保存中的 busy 状态。** 事件处理先执行 practice.reset()，原报告所称“练习待重试阻挡关闭”没有按当前调用顺序成立。
5. **记录页失败后缺少错误态属实，但并非只能整页刷新。** 顶部刷新、再次进入页面、网络恢复和轮询都有恢复路径。
6. **表达保存成功后存在多余 DOM 重建，但可见“闪烁”尚未证实。** 重建与关闭之间没有 await；本轮只确认代码执行顺序，不把 DOM 写入等同于浏览器实际绘制。

本轮没有确认达到“立即阻断发布或已造成严重泄露/破坏”的 P0。下文 P1 表示应优先处理的流程中断、草稿损失或有明确部署前提的可用性风险；P2 为一般功能、可靠性和性能问题；P3 为维护及体验改进。优先级是本次复核建议，不沿用原报告的编号。

本次只新增复核报告，未修改应用源码、原报告或真实业务数据库；测试账号与记录均置于临时数据库。未调用真实模型、未使用真实密钥，也未执行全套真实浏览器视觉验收。原报告引用的 Tether-审查报告.md 未随本次请求提供，仓库中亦未找到，故不宣称独立完成该历史原件的 26 条核对。

## 三、建议优先处理的实际问题

### R01 · P1：表达保存中的 401 会留下浮层

- **位置**：frontend/js/app.js:1271–1273、2607–2621；frontend/js/expression.js:107–124。
- **触发**：表达保存正等待 API，expression.busy=true，此时 API 触发会话失效事件。
- **证据**：401 处理清空账号并调用 closeOverlay()；该函数被 expression.busy 守卫直接挡回。控制流实验中 account=null 而 overlay.hidden=false。
- **影响**：登录视图在仍显示的表达浮层下渲染，背景还可能保留 inert 状态；正常登录恢复流程受阻。
- **修正原报告**：practice.reset() 已在关闭前运行，练习 active/pending 会清除；不能把 practice.leave() 的待重试守卫列为当前同一路径的原因。
- **建议及验收**：建立专用的会话失效收尾路径，保证解除浮层、背景 inert 和历史栈状态，并隔离迟到请求；明确未保存表达内容的保留策略。用实际表达保存返回 401 的场景验收，不只测试首页请求过期。

### R02 · P1：从引导查看资源后，关闭资源会清掉引导草稿

- **位置**：frontend/js/app.js:1847–1882、1221–1268。
- **证据**：openCrisis() 用同一个 #overlay 覆盖引导；关闭时 destroyOverlay() 将 iv.draft=null。替换浮层后关闭的实验确认草稿被清空。
- **影响**：用户查看支持资源后无法回到刚才的未保存记录与步骤。这是流程和草稿保留问题，不是已保存数据库记录被删除。
- **建议及验收**：资源页面使用独立子层，或保存并恢复调用方的引导状态；回到引导后应仍有原草稿和步骤，关闭资源不应暗中结束记录。

### R03 · P1（开放服务前）：AI 调用缺少服务端频率和并发约束

- **位置**：backend/app/api.py:887–957。
- **证据**：满足 Pro、样本量及启用配置后，连续三次 force=true 均返回 200，mock 模型调用次数为 3；代码中没有用户冷却、单用户在途去重或全局并发限制。
- **边界**：这是对成本和资源的控制缺口，并非未登录或免费用户可直接调用。实验不产生模型账单；服务商自身限额及实际代理限制未核查。
- **建议及验收**：按用户限制在途分析和最小间隔，再按部署规模设置总并发；被限制时返回明确状态与重试信息。普通缓存未命中也要防并发重复，不能只检查 force。

### R04 · P1（公网部署前）：HTTP 连接无显式超时，也无活动线程上限

- **位置**：backend/server.py:35–37、83、196–198。
- **证据**：Handler.timeout 实测为 None；继承 ThreadingHTTPServer；请求体通过 rfile.read(length) 读取，未见应用层活动连接配额。
- **影响与前提**：慢速请求体或长时间空闲连接可能占用线程。默认只绑定 127.0.0.1，实际风险取决于反向代理是否限制连接、请求体和读取时间。
- **建议**：配置连接/读取超时和独立的并发控制；在部署入口设置相应约束。单独增加 Handler.timeout=30 不能解决总线程数，也不能替代模型请求的总时限。Python 官方文档明确说明 http.server 不建议直接用于生产服务。[S3]

### R05 · P1（依赖离线使用时）：预缓存失败后仍接管并删除旧缓存

- **位置**：frontend/sw.js:35–52。
- **证据**：cache.addAll(SHELL) 失败被 catch(() => null) 吞掉，随后仍调用 skipWaiting()；activate 删除旧版本缓存。模拟资源缺失的实验确实进入 skipWaiting 和旧缓存删除。
- **影响**：新版本壳资源不完整时可能破坏原本可用的离线体验。在线页面不一定立即损坏，不能扩大为整个网站必然不可用。
- **建议及验收**：预缓存失败应使 install 失败；只有完整新版本安装成功后才清旧缓存。模拟任一壳资源 404，并验证旧版本仍可离线启动。

## 五、性能问题：保留事实，修正推断

### 5.1 静态压缩和条件缓存：成立，建议 P2

位置：backend/server.py:103–135、169–190。

向 /js/app.js 发送 Accept-Encoding: gzip 和 If-None-Match: *，收到 **200、110400 字节正文**；无 Content-Encoding、ETag、Last-Modified，仅 Cache-Control: no-cache。

本次体积复算：

| 范围 | 原始体积 | gzip level 9 | 备注 |
|---|---:|---:|---|
| 非调试 HTML/JS/CSS/JSON/SVG，共 13 文件 | 264643 B / 258.4 KiB | 79483 B / 77.6 KiB | 排除 __ 调试页和 PNG；逐文件压缩求和 |
| frontend/js/app.js | 110400 B | 32309 B | 与原报告数量级一致 |
| frontend/css/app.css | 58983 B | 13614 B | 同上 |
| frontend/js/i18n.js | 49796 B | 17022 B | 同上 |

这些数字证明文本压缩有明显收益，**不能直接等同于首屏全部网络流量**：是否首屏加载、PNG、响应头及浏览器/SW 缓存状态均未计入。304 的意思是无响应正文，不是完全没有网络开销；“二次访问 0 字节”应删除。

建议优先利用部署代理的压缩和验证缓存，或在原生服务实现等价能力；内容编码、ETag 与 Vary 应配套。API 的 no-store 策略要继续保持。

### 5.2 sw.js 每次请求重算资产 hash：成立，建议 P3

位置：backend/server.py:128–134；frontend/js/register-sw.js:5。

服务端确实在每次实际请求 sw.js 时遍历、读入并哈希所有非调试前端资产。本机连续 20 次本地 HTTP 请求平均 **11.590 ms**，范围 **8.518–33.321 ms**；这是完整请求耗时，包含网络和服务器开销，不能当作纯哈希耗时。

原报告“浏览器按规范每次导航一定下载 sw.js”的说法没有在本轮证实。页面每次 load 调用 register，不等于所有浏览器每次都会发生相同网络请求。

缓存优化有价值，但不建议只用 max_mtime + total_size 判断变化：编辑较旧文件且大小不变时可能漏判。可采用构建时版本号，或包含所有资产路径、大小、mtime_ns 的完整清单；删除/改名也应使版本变化。

### 5.3 导入去重：有优化空间，原“无索引”断言错误，建议 P2

位置：backend/app/api.py:332–357；backend/app/db.py:180–187、195–200。

逐条去重查询与逐条触发数据版本更新/缓存失效确实存在。但当前库有 user_id、occurred_at、severity 及复合索引；本次 EXPLAIN QUERY PLAN 实际输出：

~~~text
SEARCH entries USING INDEX idx_entries_severity (severity=?)
~~~

它不等于按完整去重条件高效定位：同强度候选很多时仍需过滤大量记录，重复执行可能退化；但不能表述为“每次没有索引的整表扫描”。优化器选择还受 SQLite 版本和统计信息影响。

在文件临时库、真实 schema/索引/触发器、实际 api.dispatch 导入路径上测得：

| 数据集 | 首次追加 5000 条 | 再导入同 5000 条 | 校验结果 |
|---|---:|---:|---|
| 时间戳逐秒不同、原因不同、强度均为 3 | 1.5948 s | 0.8291 s | 首次 5000 新增，第二次 5000 跳过 |
| 时间戳全部相同、原因不同、强度均为 3 | 3.9750 s | 2.2834 s | 同上 |

计时不含 HTTP 传输；样本原因文本较短。本次不支持“接近前端 30 秒超时”的推断，也不能保证大历史库、长文本或慢磁盘的表现。原报告 76 倍微基准未附脚本、schema 和查询计划，不能当作本项目修复收益承诺。

可评估集合去重或更合适的查询/索引，但集合也会占用内存，且必须在同一事务内处理输入内部重复。**不要直接按原建议临时移除 entries 触发器**：它们承担账号缓存失效和数据版本一致性，需要完整替代及并发测试后才可调整。

### 5.4 AI 缓存读路径清理全表：成立，建议 P2

位置：backend/app/ai.py:498–527。

实际查询计划：

~~~text
当前 julianday(created_at) 清理：SCAN ai_cache
直接 created_at <= ? 的对照：SEARCH ai_cache USING INDEX idx_ai_cache_created (created_at<?)
~~~

一次 cache_get() 的 SQL trace 为 BEGIN → DELETE FROM ai_cache … → SELECT payload … → COMMIT。由此可以确认“读缓存会启动写事务”，存在并发写竞争的结构性风险；未进行生产负载或锁等待压力测试，原微基准加速倍数不作为本次结论。

修改时有两个约束：

- **不能只删 cache_get() 中的 prune。** 现有 SELECT 没有过期过滤，简单删除会让超过 24 小时的缓存被返回，直到后台下次清理。读路径仍应校验 TTL。
- 字符串时间比较只有在格式、精度、时区统一后才可靠；迁移/异常时间值必须另行处理，不能牺牲现有 malformed-cache 用例。

### 5.5 每请求多次连接：数字属实，建议 P3

patch db.connect 计数确认：登录状态 GET /api/bootstrap **6 次**，PATCH /api/entries/{id} **4 次**。

backend/app/db.py:148–154 每次执行 mkdir、连接及 PRAGMA。可按实际负载评估请求内复用；没有证据表明当前小规模部署必须引入连接池。SQLite 实测 busy_timeout 为 **5000 ms**，因此原建议“加 timeout”只能理解为显式配置，并非目前没有数据库锁等待超时。[S4]

不把 synchronous=NORMAL 当作无条件修复：它涉及断电持久性取舍，应结合部署需求决定。跨线程复用连接也不能只凭 check_same_thread=False 认定安全。
